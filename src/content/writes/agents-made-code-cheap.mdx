## The cost moved

A year ago, trying an idea meant a week of plumbing before you learned anything. Now an agent can stand up a working prototype before lunch. The code didn't stop mattering, but it stopped being the slow part.

What got expensive is everything around the code: knowing which problem is worth solving, describing it well enough that a person or an agent can act on it, and having the judgement to throw away the version that doesn't work. <Side>this is the whole post, honestly</Side>

If writing code is cheap, then writing the <mark>wrong</mark> code is also cheap. That sounds like good news until you notice it's now very easy to ship a lot of the wrong thing, very quickly.

## Become the expert first

The best requirement I ever got was the one I wrote myself after sitting with the people doing the work. Before any box gets drawn, I want to be the person in the room who understands the process best, the edge cases, and the reasons behind the weird spreadsheet.

Agents are fluent in code. They aren't fluent in your business. That gap is where engineers now earn their keep. <Side>SME first, engineer second</Side>

## Write the context down

Context engineering sounds like a new discipline. Mostly it's an old one: writing a very good brief. The goal, the constraints, a couple of examples, what "done" looks like, and the decisions you've already made so nobody relitigates them.

```md title="brief.md"
## Goal
Approvals finish in one place, not over email.
## Constraints
- SSO only, three roles, finance stays the source of truth
- No new infra unless something needs real time
## Done means
- An approver can clear their queue from their phone
<!-- decisions so far: notifications are a table, not a queue -->
```

A brief like this makes a new teammate useful on day one. It makes an agent useful in the first prompt. Same document, two readers. <Side>I keep one per project now</Side>

> Structure is what lets you move fast _without_ breaking things.

## Fail fast, on purpose

When a branch costs nothing, the risky idea should go first. I'd rather learn on Tuesday that an approach doesn't hold than discover it in week three. So I prototype the scary part, keep the boring parts boring, and write down why each decision went the way it did.

- Spike the riskiest assumption in a throwaway branch.
- Pick the boring option unless the evidence says otherwise.
- Delete the spike. Keep the notes.

## What I'd tell myself

Typing speed was never the job. Understanding the people, writing the context down and owning what ships were always the job. Agents just made it obvious.

<Tldr>

- Code got cheap. Understanding didn't.
- Be the expert before you write the brief.
- Write the brief like a person and an agent will both read it.
- Fail on purpose, early, and keep the notes.

</Tldr>
